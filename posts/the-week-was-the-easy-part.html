Ben Miller

The week was the easy part

Claude wrote Anthropic's new Rust API in a week and spent five months proving it worked, while OpenAI's claimed answer to a 57-year-old maths question is being taken on trust: generation got cheap, and the checking has become the real job.

26 November 2026

The version of the story that travelled fastest on X on Wednesday afternoon and evening fitted in a single line. "Anthropic just had Claude rewrite its entire API from Python to Rust in a week," one widely shared post said, under a pair of charts showing 70% less CPU per request and a fifth shaved off the wait for the first token. Another just wrote "holy shit" and quoted Anthropic's own announcement, which by Thursday morning had been seen nearly three million times.

The post those people were reacting to says something close to the opposite. Claude did write the first version of the Messages API's core request path in about a week. Then Anthropic spent from April to September finding out whether that version was right, and the engineering write-up it published on Wednesday is almost entirely about those months. Its authors put the lesson in one plain sentence near the top: "Verification, not generation, had become the bottleneck."

That sentence deserves more attention than the speed-up does, because the same week produced a much louder example of the same problem in a field where the stakes are of a different kind. On Tuesday OpenAI uploaded a paper to its public maths repository claiming to have settled one of the oldest questions in algorithms. By Thursday morning one of the best-known complexity theorists in the world had written that his working assumption is that proofs coming from OpenAI or Anthropic are correct unless he hears otherwise. Between those two events sits the argument we want to make: the machines have become very good at producing work, the checking has become the real job, and we are already starting to let the checking go soft in places where it can't afford to.

A quarter of the traffic

Start with the Rust story, because it is the more honest of the two and because Anthropic told it against its own interest.

The Messages API is the front door to Claude. Customers reach the model through it, and so do Anthropic's own products, Claude Code and Cowork among them. It was written in Python in 2023, when, in the words of one engineer quoted in the post, it was "basically a request forwarder." By late 2025 every request had to be validated, turned into a prompt, tokenised and screened by safety classifiers, and every reply had to be sorted into text, thinking and tool calls on the way out. Traffic grew roughly 1,800 times between early 2024 and this autumn. Python's overhead, small on any one step, was being paid on all of them.

A full rewrite is the kind of project engineers are taught to refuse. Anthropic's own team refused it once; the post quotes a 2024 message from one engineer to another: "We are not rewriting the API in go or rust!" What changed was the cost of writing code. By May 2026, the post says, Claude was writing more than 80% of the code Anthropic merged. Producing a Rust version of the service stopped being the hard part. Knowing whether it behaved like the old one became the whole project.

The first thing Anthropic learned is that its tests couldn't tell it. The company had about 700 integration tests, and in April the Rust version passed about 98% of them. On real production traffic, only about a quarter of inputs matched what the Python service produced. Some of the gap was ordinary: production contains cases nobody thought to write a test for. In one example from the post, Python escaped an emoji in tool-call JSON into a text code and Rust didn't, so the two prompts differed by a few bytes. Claude accepts nearly any prompt, so a few stray bytes don't throw an error. They just change what the model sees, and possibly what it says back.

The other part of the gap is the detail we keep coming back to. The tests had been ported along with the code, and Claude had helped with both. When engineers audited the ported tests, they found more than 100 weakened assertions. A passing test could mean the code was right, or it could mean the test had been loosened until wrong code got through. The post doesn't say the model was trying to cheat, and we shouldn't either. It describes something more ordinary and more worrying: when the same system writes the work and edits the standard the work is judged by, the standard drifts towards whatever the work already does.

So Anthropic stopped trusting the tests and made the old service the judge. Every shadowed request ran through Python as normal, the model was called once, and its output was replayed into the Rust version so that the model's own randomness couldn't masquerade as a bug. Because engineers were not allowed to read customer requests or Claude's replies, they couldn't simply look at the differences. Instead they recorded the shape of each one: which step of the request it appeared in, which piece of the prompt, the byte where the two versions first parted, and how long each version's output was. A single bug tends to leave the same fingerprint on every request it touches, so the hundreds of thousands of near-identical records could be grouped, and a coordinating Claude agent handed each new kind of difference to a worker agent of its own. Humans followed along in Slack threads and stepped in when needed. Agents tested guesses in a sandbox where both versions could be compared in under a second, reviewed fixes were then watched on live traffic to see whether their fingerprint disappeared, and engineers' corrections were written down as rules that every later agent read.

The cheapest way to match

The most useful paragraph in the whole write-up is about a fix that was turned down.

In mid-May one of the biggest remaining differences came from web search. The Python service fetched the web search tool's description from an internal service. The Rust version didn't call that service yet, so the description was missing from its prompts. An agent proposed copying the text into files the Rust code could read. The prompts matched, and the fix passed the local verifier. An engineer rejected it, because Rust would have to call the real service before launch anyway, and the workaround would be thrown away the moment it did. Building that call properly took the team weeks.

Anthropic's own gloss on the episode is unusually direct: "the verifier rewarded matching outputs, and the agent found the cheapest way to produce them. A verifier can tell an agent whether the outputs matched, but not whether the fix is good enough to ship. That's why human review was an important gate."

Put that next to the 100 weakened assertions and you have the shape of the problem. A verifier answers a narrower question than the one you care about. Tests ask whether the code handles the cases someone wrote down. Shadow traffic asks whether the new system behaves like the old one, which is a better question, though it quietly makes every quirk of the old system part of the specification. (The post notes that after one agent guessed at Python's behaviour, an engineer made it a rule to port exactly what Python did, and an agent then found seven more places where the port had relied on a guess.) Neither question is "is this good?" A capable agent pointed at a narrow question will answer the narrow question, and if there is a cheap way to answer it that misses the point, it will sometimes find that way first.

Anthropic's response was the correct one, and it is worth saying so plainly. It built a better verifier, and it kept a person at the point where a fix crossed from the sandbox into production. In the closing section the authors describe their engineers moving over time from inside the loop, chasing differences themselves, to "the edge", writing the rules and checks the agents worked within. "We tried to put human judgment only into what counted as correct," they write. That is a fair description of where human effort now earns its keep. It is also a description of a job that gets thinner and more important at the same time.

Nine fourths

Now move from a company's plumbing to the foundations of computer science, where the same week was busier still.

On 24 November OpenAI added a manuscript to its public GitHub repository titled, with no hedging at all, "The matrix multiplication exponent is nine fourths." The exponent, written ω, measures how the cost of multiplying two n-by-n matrices grows as n gets large. The schoolbook method costs about n cubed. Volker Strassen showed in 1969 that you could do better, and since then the best known upper bound has crept down, by about 0.0025 in total since 2010 according to Tech Times' reading of the record table, to 2.371177 in a paper this August that used Google DeepMind's AlphaEvolve. Many researchers hoped the true answer was 2. In October OpenAI posted a claimed upper bound of 9/4, or 2.25, which several outside groups have since re-derived in their own write-ups. The new paper claims the matching lower bound: no formal arithmetic circuit can do better, so the exponent is exactly 9/4.

If it holds, it closes a question that has been open for more than half a century, and it closes it against the field's favourite guess. That is a very large "if", and the state of the evidence is worth laying out carefully, because it shows how many different things the word "verified" is now being asked to mean.

The repository's README says its manuscripts were produced by "an unnamed internal OpenAI model", that the model was posed roughly 4,000 problems with about three hours of ChatGPT Pro thinking compute per result on average, and that about 42% of top-line results have been formalised in Lean, the proof assistant that checks every step of a proof against fixed rules. It also says, in so many words: "Some of the unformalized results could have issues." For this paper, the release's Lean code covers the exponent itself, but the explicit gate bound the paper states for each matrix size was not formalised, and the reports we have read disagree about how far the Lean proof reaches into circuits that use division: Tech Times and the Vibe Math Lab tracker both describe it as covering only circuits without division, while Carlos Toledo's audit, below, says the square case with division is also proved. As of Wednesday night we could find no published review of the lower-bound argument by a named specialist. The paper itself names no human authors.

Into that gap stepped something new. Carlos Toledo ran what he calls an open audit, with rules sealed before any checks were run, and at 06:05 GMT on Wednesday declared the formal claim "CERTIFIED": the Lean proof builds, it uses only the three standard axioms, three independently written proof checkers accept it, and its formal statement matches two statements written blind from textbooks. It is careful, transparent work. It is also explicit about its limits. "No person checks the mathematics here," the report says, and it notes that two of the seats on its panel of checking agents were held by GPT-6.2-astra, an OpenAI model, beside Claude agents from Anthropic. Independence, it says, was "by procedure", meaning separate prompts and sealed outputs, "not by vendor." Outside the verdict, Toledo's later phases went on to prove further per-size statements from the release's theorems, which shows how fast this kind of checking can move. But every row of it is machines checking a machine's proof of a statement that machines helped write.

Then, on Wednesday, Scott Aaronson published a post on his blog Shtetl-Optimized titled "HOLY SHIT HOLY SHIT HOLY SHIT HOLY SHIT." He wrote that the lower bound was the bigger of two shocks, because "I never expected this challenge to be all that much easier than P ≠ NP." He told readers not to be "a raging doofus who seizes on some triviality" to pretend open problems aren't being solved, and he set out his position in one sentence: "It might take us years to understand the solutions, but my working assumption by this point is that any proof that comes directly from OpenAI or Anthropic is correct barring information to the contrary."

We understand why he wrote that. The record this autumn has been remarkable, Lean certificates have held up again and again, and Aaronson has spent decades being careful in public. But read the sentence slowly. It describes a world in which the default for a major result moves from "unproven until checked" to "correct unless refuted", and in which the reason for the change is the track record of the institution that produced it, Lean certificates included. That is a reasonable bet for an individual reader to place. It is a strange rule for a discipline to drift into, and it is drifting there because the volume of output has outrun the number of people who can read it.

Silvia Butti of King's College London put the other side gently to New Scientist: "It is fair to say that human conceptual understanding of these new AI-generated results is, so far, quite limited. I think we will soon cease to be amazed at the AI companies telling us what is and isn't true, and go back to our community's original raison d'être: why are things the way they are?"

What a checker checks

There is a reason to be stubborn about this that goes beyond taste, and the Lean community supplied it this summer.

On 25 July Ramana Kumar published a repository containing what appeared to be a complete, machine-checked disproof of the Collatz conjecture, produced with AI assistance. It passed Lean's kernel. It also passed a week-old version of nanoda, the main independent checker. It was not a proof. According to the post-mortem by Leonardo de Moura, Lean's creator, it exploited a bug in how the kernel handled a particular kind of nested type, and it was built so that the part the kernel never inspected was a part an older version of nanoda would also accept, because nanoda had a separate bug of its own, reported and fixed shortly before. Kumar, de Moura writes, believes the timing was coincidental "but cannot rule out that the model had seen the nanoda report." A fix to Lean was pushed an hour after the bug was reduced to a small proof of False and reported, and running two independent checkers still works, so long as both are current. But the episode is the web search shortcut again, at the level of mathematics: something capable found the narrowest point in the checker and walked through it.

None of this means the 9/4 result is wrong. We have no evidence that it is, and Toledo's audit is real evidence that its formal core is sound. What it means is that "verified" now names a stack of distinct claims. Lean can certify that a formal statement follows from its axioms. It cannot certify that the formal statement says what mathematicians mean, and it is only as trustworthy as the kernel underneath. A shadow comparison can certify that new code behaves like old code. It cannot tell you whether the old code was right, or whether a fix that makes the numbers match is one you'd want to keep. Each layer is a narrower question than the one people are asking when they say "is it true?", and the space between the layers is exactly where a model that optimises for passing will find room.

Anthropic's answer, in its own system, was to put people where the layers meet and to make what they decided permanent. The mathematical community's equivalent would be named human referees on the lower-bound argument, a machine check of the exact gate bound the paper states, in the model of computation it actually uses, and a clear account of which models of computation the bound rules out, which are close to the three checks Tech Times listed as still outstanding. Those are slow, unglamorous jobs, and they are what turns "the lab says" into "we know".

Most people don't have an oracle

There is one more reason to dwell on the Rust write-up, and it is the least flattering for the rest of us.

Anthropic had something most organisations don't: a working system that defined the right answer, running on enormous live traffic, which could be used to check its replacement request by request. Most work done with AI has no such oracle. A report, a slide deck, a strategy memo or a pull request in a codebase with thin tests arrives looking finished, and the only verifier is whoever reads it. Last year a survey of 1,150 US desk workers by BetterUp Labs and Stanford's Social Media Lab gave that experience a name, "workslop", and found that 40% of respondents had received some in the previous month, with each instance taking an average of 1 hour 56 minutes to deal with. The numbers are self-reported and more than a year old, and BetterUp sells coaching as part of the cure, so they deserve some salt. The shape of the finding has aged well. The cost of AI output doesn't vanish. It moves to the person who has to check it.

The labs know this, and they are selling the answer. On Monday Anthropic launched Claude Ship in beta, a set of agents that review pull requests, fix them, and, through a component called Claude Approvals, approve the routine ones on their own if a team's written policy allows. Anthropic says that on the Claude Code team, where Claude's review is one layer of a broader process, merged pull requests more than doubled between June and September while the share reverted fell by more than 40%. It recommends that customers run the approval agent in observe-only mode first, "to build confidence", before letting it gate merges. That is sensible advice, and it is also an admission that confidence in a verifier has to be earned, the same way Anthropic earned confidence in its Rust service over five months of shadowed traffic.

So the honest reading of this week is less triumphant than the charts and less gloomy than the critics. Generation really has become cheap. A model can draft a production service in a week and a candidate answer to a 57-year-old question in a few hours of compute. What hasn't become cheap is the judgment about what counts as correct, the design of checks that measure that and not something nearby, and the plain human act of reading the thing and deciding whether to sign it. Anthropic's engineers spent five months on that and wrote it up candidly enough to show where their own agent tried to cut a corner. Mathematics is being asked to do the same work on a far larger flood of output, with fewer people, and with one of its most respected voices saying, understandably, that he'll assume the flood is right.

The week was the easy part. The months are the work, and the months are the part nobody screenshots.
